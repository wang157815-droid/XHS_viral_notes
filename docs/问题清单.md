# 全项目审查问题清单与修复方案

## 摘要
本轮按“全项目”范围做了只读审查，覆盖新后端、遗留系统、前端、Docker/配置、测试体系与依赖环境。未修改代码。当前最需要优先处理的是：测试体系不可用、导出数据源契约不稳定、JSON 文件存储在多进程下有一致性风险、部署目标混乱、安全配置过宽。

## 问题清单

- **P0 测试体系当前不可用**：`pytest` 在创建/清理临时目录时触发 `PermissionError [WinError 5]`，导致后端回归测试无法执行。需要先固定 pytest 临时目录和缓存目录权限，否则任何修复都缺少可靠验证闭环。
- **P0 Sheet3/4/5/6 数据源契约仍会被 crawler fallback 破坏**：[crawler_agent.py](E:/redMuse/XHS_viral_notes/backend/app/application/agents/crawler_agent.py) 中仍存在把 `industry/all_notes` 回填到 `top_interaction`、`serp_top` 的逻辑；这会导致 Sheet3/4/5 展示内容有时相同。导出层 Sheet3 合并逻辑基本正确，但上游四源视图不是严格隔离。
- **P0 JSON 文件存储不适合当前多进程部署**：`TaskRepository`、`TaskContextStore`、`KnowledgeRegistry` 依赖本地 JSON + 进程内锁；Docker 同时有 Web 与 ARQ Worker 共享 `datas/`，多进程写入存在丢写、覆盖、状态不一致风险。
- **P1 Docker 部署目标与项目主线不一致**：[Dockerfile](E:/redMuse/XHS_viral_notes/Dockerfile) 默认运行 `viral_app.py` 端口 8000，但 AGENTS 说明新后端是 `backend/run.py` 端口 8100；这会让部署环境实际跑遗留系统，而不是 RedMuse 新后端。
- **P1 CORS 配置过宽且与凭证模式冲突**：[main.py](E:/redMuse/XHS_viral_notes/backend/app/main.py) 使用 `allow_origins=["*"]` 且 `allow_credentials=True`，生产环境不安全，也可能导致浏览器凭证请求行为异常。
- **P1 Python 依赖存在实际冲突**：`pip check` 报告 `gradio` 与 `pydantic 2.12.5` 不兼容，`transformers` 与 `tokenizers 0.22.2` 不兼容。运行时可能出现隐性导入错误或模型能力异常。
- **P1 版本控制状态不健康**：`git status` 显示 `backend/`、`frontend/` 等大量核心目录为未跟踪状态，同时遗留文件大量修改。当前不利于审查、回滚、协作和发布。
- **P1 异常吞噬较多，影响故障定位**：项目里存在大量 `except Exception: pass` 或只降级不记录关键上下文的代码，例如编排、任务上下文、LLM provider、SEO 提取、遗留服务等位置。真实线上问题容易被静默掩盖。
- **P1 Sheet5 业务命名与目标不完全一致**：[excel_exporter.py](E:/redMuse/XHS_viral_notes/backend/app/services/canvas_export/excel_exporter.py) 中 Sheet5 仍有“互动 TOP / 品类互动top”语义，而你的目标是“本品数据”。即使数据源修好，用户看到的表头也可能误导。
- **P2 前端 lint 只有一个非阻塞警告**：[module-card.tsx](E:/redMuse/XHS_viral_notes/frontend/src/components/workspace/module-card.tsx) 约 660 行使用 `<img>`，Next.js 建议改为 `<Image />`。
- **P2 测试文件存在转义警告**：[test_notes_vector_store_sql.py](E:/redMuse/XHS_viral_notes/backend/tests/test_notes_vector_store_sql.py) 第 1 行附近存在 `invalid escape sequence '\w'` 警告，需要改 raw string 或双反斜杠。

## 修复方案

- **先修测试基础设施**：固定 `PYTEST_ADDOPTS` 或测试配置里的 `--basetemp`、cache 目录到项目内可写目录；清理当前不可访问的 `.pytest_cache`；确保 `python -m pytest backend/tests -q` 能稳定启动。
- **再修四源数据契约**：Crawler 层必须保证 `competitor`、`top_interaction`、`serp_top` 独立来源，不允许用 `industry/all_notes` 兜底污染维度；缓存命中与实时爬取都统一走同一个四源规范化函数。
- **同步更新测试契约**：把现有断言“允许 fallback”的测试改成“缺哪个源就空哪个源或标记缺失”，新增缓存命中、实时爬取、部分源缺失、全部源齐全四类测试。
- **收敛存储一致性风险**：短期为 JSON 写入增加跨进程文件锁和原子写；中期把任务、上下文、知识库元数据迁移到 PostgreSQL，JSON 只保留调试导出或备份。
- **明确部署主入口**：如果当前主线是新后端，Docker 应运行 `backend/run.py` 或 uvicorn `backend.app.main:app`，并调整端口、healthcheck、nginx upstream；遗留系统单独作为 legacy profile。
- **收紧安全配置**：生产环境 CORS 改为明确前端域名；JWT secret 只允许环境变量提供；前端 localStorage token 风险需要通过 CSP、XSS 清理和后续 httpOnly cookie 方案降低。
- **整理依赖与版本控制**：锁定一组可通过 `pip check` 的依赖版本；把核心目录纳入版本控制或明确拆分仓库策略；避免继续在未跟踪核心代码上做大规模改动。
- **提升可观测性**：静默异常至少记录模块、任务 ID、输入摘要和降级原因；对 crawler、export、LLM、任务状态写入这几类关键路径优先处理。
- **修正文案与编码**：Sheet5 文案统一为“本品数据”；修复确认存在的乱码 docstring；保留 UTF-8 编码，不根据 PowerShell 显示结果批量替换中文。

mod-draft-workbench 前后端契约不一致
后端明确写了草稿区不生成 paragraph_id、不支持细粒度反馈，但前端 canvas-adapter.ts 给草稿 6 字段生成了可编辑段落 ID，并展示编辑/删除反馈 UI。后端重生执行器对非矩阵/洞察/样本模块只是把状态改回 READY，不会真正应用草稿编辑或删除。所以草稿段落的删除/编辑刷新后容易“复活”。
相关文件：backend/app/application/agents/canvas_render_agent.py、frontend/src/components/workspace/canvas-adapter.ts、backend/app/application/module_regeneration.py

“删除段落”目前更像反馈标记，不是真删除
EditableParagraph 点击删除后只在本地隐藏，并向后端写 feedback_map[action=delete]。刷新画布后，前端只把 like/dislike 映射为视觉状态，delete 不会让段落继续隐藏。矩阵/痛点/SEO/样本在“重生”时会消费 delete，但草稿和普通 editable 段落不会。
相关文件：frontend/src/components/workspace/module-card.tsx、backend/app/application/paragraph_feedback.py

重生失败被降级成 READY，用户可能误以为成功
run_module_regeneration 捕获异常后把模块状态写回 READY，再发 error 事件。这样 UI 上模块不一定表现为失败，内容也可能是旧内容，容易误导用户“已重生”。更合理的是写 FAILED 或保留明确的 dirty_reason/error。
相关文件：backend/app/application/module_regeneration.py

测试覆盖偏确定性，缺少真正的端到端回归
现有 test_paragraph_feedback_and_regen.py 覆盖了 API 持久化、reset、路由解析、后台任务调度，但没有覆盖 LLM patch 合并后的真实模块内容变化、delete 刷新后是否隐藏、前端版本冲突后的重试体验。
相关文件：backend/tests/test_paragraph_feedback_and_regen.py
